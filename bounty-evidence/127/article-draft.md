# What an MCP documentation page must explain before an agent can use it

An MCP server can expose dozens or hundreds of tools, but a tool count alone does not make the server usable. The difficult part begins when a developer or an agent has to decide which tool to call, what arguments it accepts, and what evidence should be kept after the call. I learned this while helping document the Perseus Vault MCP surface, a security-oriented project with 173 tools in its published reference.

The first useful step was to document the protocol surface from the source instead of writing a hand-maintained list. On August 28, 2026, the [Sourcey open source page](https://sourcey.com/oss) stated that its MCP support renders tools, resources, and prompts as browsable reference pages, with JSON-RPC, TypeScript, and Python examples. That matters because an MCP client does not need another marketing overview. It needs the exact method name, input shape, and a concrete request that can be adapted to its runtime.

A good tool page should answer four questions quickly. What does this tool do? Which fields are required? What does a valid call look like? What should the caller expect back? When those answers live together, a person can inspect the contract and an agent can extract the same structure. In the Perseus work, the generated reference gave each tool its own location instead of placing 173 names in one enormous page. This made spot checks possible and gave maintainers stable links for individual operations.

The second requirement is reproducibility. Documentation generated from an MCP manifest can drift if nobody records which source produced it. We pinned the source commit, recorded the adapter command, and compared the published page with the current tool surface. The audit also sampled named tools rather than trusting the total count. A page can report 173 tools and still be wrong if names, descriptions, or schemas come from an older release.

On August 28, 2026, [Sourcey's repository](https://github.com/sourcey/sourcey) described MCP documentation as browsable reference with JSON-RPC, TypeScript, and Python code samples. The same repository documented a build-time model: it renders the site without requiring dashboard calls or a framework runtime to display the documentation. For an MCP project, this is practical. The resulting files can be served by the project's existing site, reviewed in a pull request, and rebuilt in continuous integration when the source changes.

The third requirement is a useful machine-readable companion. On the same date, the [Sourcey open source page](https://sourcey.com/oss) said that one build produces structured HTML, a JSON search index, and llms.txt. It also stated that llms.txt and llms-full.txt are generated as alternate views of the same documentation graph. This is more valuable than attaching an unrelated summary after the site is built. Human pages and agent-oriented context should describe the same tools from the same input.

There is also a governance lesson. A generated site is not adopted documentation merely because somebody can host a preview. The project must accept the change and serve it on infrastructure it controls. For Perseus Vault, the documentation contribution went through an upstream pull request and the final reference appeared on the project's own perseus.observer domain. That distinction separates a demonstration from documentation the maintainers can update and stand behind.

If I were reviewing MCP documentation for another project, I would use a short checklist. Every tool needs a stable page and an exact input contract. Examples should use the protocol and languages real clients use. The source revision and generation command should be recorded. A reviewer should compare several published tools with the manifest. Search and agent context should come from the same build. Finally, the project should own the published URL and the update path.

MCP documentation succeeds when it reduces uncertainty at the moment of use. A developer should not have to search the server implementation to discover a required field. An agent should not have to guess whether a description belongs to the current release. A maintainer should be able to regenerate the reference and review the change. Those are ordinary documentation goals, but MCP makes failures more expensive because automated callers act on what the page says.
